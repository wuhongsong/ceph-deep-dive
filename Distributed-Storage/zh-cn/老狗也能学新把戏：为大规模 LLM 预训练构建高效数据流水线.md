# 摘要（Abstract）

数据流水线对运行在数千 GPU 上的大规模预训练作业的性能起关键作用。本文对生产负载的数据访问模式做了全面的定量分析，揭示三个此前报道不足的瓶颈。**第一**，用远端 checkpoint 评测训练中模型时，跨数据中心流量成为主要延迟来源。**第二**，启动阶段的 checkpoint 加载频繁遭遇 I/O 争抢，延迟作业初始化。**第三**，加载过程中的数据转换对多模态模型而言成为显著的、CPU 密集的瓶颈。

据此提出三项优化：**基于全局命名空间的预测式 checkpoint 复制**、**主动式热文件复制**、**把数据转换卸载到存储层 CPU 资源**。关键在于，作者论证这些优化并非特定系统专属，而是针对 LLM 时代的**根本性架构错配**；它们对老旧系统与现代存储系统同样适用，提供了一条以**最小工程侵入**升级基础设施的高回报路径。合计效果：每次评测浪费的 GPU 小时从 16,800 降到 4,000；每次训练启动的 checkpoint 加载时间缩短 40.8%；数据加载引起的训练停顿减少 63.2%。

# 1 引言

基础模型训练已经改变了系统基础设施的重心。训练超过 1000 亿参数的模型，如今需要在大规模集群上协调数千 GPU 长时间运作。系统社区已经激进地优化了计算调度与网络集合通信，以最大化模型 FLOPs 利用率（MFU）。然而，负责加载、转换、投递 EB 级训练数据的**数据流水线所受到的审视却少得多**。

这种忽视是要紧的，因为数据流水线不再是一个被动的工具设施——它是首要的性能决定因素。作者的环境管理着从十亿参数文本模型到万亿参数多模态模型的各类任务，并选用 **HDFS** 作为存储骨干，理由是它成本效益好、具备承载 EB 级数据的容量。

作者分析了 **90 天内收集的 3 万条训练作业 trace**，以刻画现代预训练作业与传统存储架构之间的交互。分析揭示三个在通用存储系统面对大模型训练的极端规模时浮现的瓶颈：

**第一，跨 DC 延迟陷阱（Cross-DC Latency Trap）。** 为保证模型质量，生产训练依赖"**伴随评测**（companion evaluation）"——一条带外验证流水线，周期性加载近期 checkpoint 并与训练并行地跑 benchmark 套件。由于评测作业的调度与硬件需求不同于训练，它们往往运行在远端数据中心。作者发现，跨广域网抓取 checkpoint 分片受制于**成千上万次小张量读的往返时延，而不是可用带宽**。这种延迟主导造成严重延误，浪费数百万 GPU 小时。

**第二，初始化 I/O 风暴（Initialization I/O Storm）。** 大规模训练因调试或故障而频繁重启。作业初始化触发同步的读操作激增，数千 worker 争抢**极少量热文件**（如全局元数据与共享 embedding 参数）。这种争抢打满存储节点，制造出阻塞整个集群的尾延迟。

**第三，转换之墙（Transformation Wall）。** 与纯文本模型不同，多模态训练涉及视频与图像解码这类 CPU 密集的转换。作者证明训练节点的宿主 CPU **跟不上 GPU 的消费速度**，这把瓶颈从存储 I/O 转移到了本地计算，造成显著的流水线停顿。

作者的论断是：**这些瓶颈之所以长期存在，是因为存储系统以"反应式"运作，而训练负载本质上是"确定性"的。** 为此提出三项把应用层模式暴露给存储层的软件定义优化：

- **预测式 checkpoint 复制**：利用评测作业的规律排期来复制 checkpoint，并对紧急反馈信号赋予优先级。伴随评测 I/O 时间减少 **76.1%**。
- **主动式热点预测**：实现一种协同机制，训练框架在执行前把热文件告知存储系统，存储层主动复制这些文件以疏散 I/O 风暴。Checkpoint 加载时间减少 **40.8%**。
- **存储侧转换卸载**：利用存储节点上未被充分使用的 CPU 做数据处理。这个 Just-in-Time 机制让转换与训练流水化，数据加载停顿减少 **63.2%**。

**三点贡献**：
1. 用生产 trace 刻画预训练数据访问模式，识别三个长期被忽略的关键瓶颈：伴随评测的跨 DC 延迟陷阱、同步初始化 I/O 风暴、多模态转换之墙。
2. 提出利用负载确定性的软件定义优化：预测式 checkpoint 复制掩盖延迟、主动式热文件复制疏散争抢、存储侧卸载承接 CPU 密集转换。这些优化大幅减少浪费的训练时间、提升整体效率。
3. 论证这些优化可作为应对 LLM 时代架构错配的**可泛化框架**。通过弥合基础设施与训练之间的鸿沟，提供演进通用存储以满足 LLM 需求的实用蓝图。作者在生产环境中验证了这些发现，并计划在匿名化后发布 trace 以支持后续研究。

# 2 背景与动机

## 2.1 预训练数据流水线

作者介绍了在生产环境中支撑数千至数万 GPU 预训练作业的数据流水线架构。选择 HDFS 的原因是：它是**现成的、成本效益高的、能容纳 EB 级数据的基础设施**。如图 1 所示，流水线由两个主要组件构成：**存储层**与 **dataloader**。

**存储层**持久化预训练所需的全部产物：
- **训练数据集**：涵盖文本、图像、视频等异构模态。
- **Checkpoint**：包含元数据以及模型参数与优化器状态的分片张量，是训练进度的权威记录。
- **Logits**：每次前向传播后输出的原始、未归一化的预测向量；训练本身通常不用它，但它对调试与监控模型行为很关键。

**Dataloader** 位于存储与训练框架之间。它把原始数据转换成模型期望的格式，并协调数据经 CPU 内存搬运到 GPU。转换操作包括计算密集的步骤：视频与图像解码、视觉输入的空间缩放、文本的 tokenization 与序列打包。因此 dataloader 兼具**转换引擎**与**暂存机制**双重身份，负责准备数据并高效流水化地送入加速器栈。

预训练作业通过**两条 I/O 路径**与数据流水线交互：
1. 在从 checkpoint 初始化、持久化 checkpoint、输出 logits 时，直接对存储层读写；
2. 并行地通过 dataloader 获取训练数据，后者执行存储读取与样本转换。

这两类交互共同定义了施加于存储子系统的**稳态**与**突发**I/O 模式。

作者把预训练执行刻画为**三个阶段**，各有不同的数据访问行为：

**初始化阶段**：训练框架在关键路径上发出阻塞操作。具体来说，它从存储层加载完整模型 checkpoint（含参数与优化器状态）。这些张量按所采用的并行化策略，被分发或复制到数千个 **rank**（参与分布式训练的 worker 进程，通常每个独占一块 GPU）。

**迭代训练阶段**：初始化之后作业进入这一阶段，执行一连串**训练步（step）**。作者把 step 定义为处理完整一批数据、在必要的前向与反向传播之后完成一次模型参数更新。这一阶段中，存储访问与 GPU 计算基本异步进行：dataloader 持续为未来的 step 预取并转换数据，训练框架在每次前向后写 logits、并周期性把 checkpoint 持久化到存储。这些活动在整个训练过程中产生持续的读写流量。

**伴随评测阶段**：周期性地与迭代训练并行，运行在独立的评测集群上——因为评测相对训练通常有不同的调度与资源需求。由于 loss 这类训练指标往往不足以检测质量退化或模型崩溃，伴随评测通过在近期 checkpoint 上、用与训练集不同的数据（即真实世界 benchmark）评估模型，提供对进展的**外部度量**。每个评测周期从存储加载最新 checkpoint，把分片张量合并为统一格式，然后加载合并后的 checkpoint 与 benchmark 套件，最后执行推理并把结果写回存储。虽然逻辑上与训练分离，但伴随评测的结果可以**回馈到训练控制面并触发回滚**。

## 2.3 浮现的存储挑战

预训练过程中，不同数据类型在生命周期的特定阶段被访问，往往产生占据总时间线相当比重的 I/O 操作。本文刻画各阶段固有的独特 I/O 瓶颈，并给出对应的生产机制。

**1. 伴随评测中的跨 DC I/O（§3）。** 伴随评测对验证预训练模型至关重要，但受制于因调度与硬件约束而必须从远端（跨 DC）训练集群抓取 checkpoint。这带来两大 I/O 挑战：一是"**小 I/O 延迟陷阱**"——抓取成千上万个小张量受制于 WAN RTT 而非带宽；二是来自并发后台任务的**严重带宽争抢**。为缓解这些问题，作者引入**预测式 checkpoint 复制**（利用规律的评测间隔提前流水化并批量化 checkpoint 复制）与**信号驱动的优先级**（把带宽分配给由训练异常触发的紧急评测）。

**2. 初始化 I/O 风暴（§4）。** 初始化阶段受制于一场"I/O 风暴"——同步的 checkpoint 加载在极少量热文件（如全局元数据与被复制的参数）上触发大规模数据争抢。这种争抢打满存储节点，制造出阻塞整个集群、浪费大量 GPU 周期的 straggler 读。为此作者引入**主动式热点预测**：一种协同机制，训练框架把确定性的访问模式显式告知存储层，使系统能在作业启动前**预先复制热文件**，疏散争抢、把不可预测的尾延迟转化为常数时间的访问。

**3. 转换之墙（§5）。** 对多模态（如 MM-L）预训练，数据加载因视频与图像转换（解码、裁剪等）的高成本而**从 I/O 受限变为计算受限**。这道"转换之墙"造成严重的 straggler 问题——宿主侧处理缓慢逼迫 GPU 空转，在迭代训练阶段浪费大量算力。而离线转换因**极端的存储放大（50×∼100×）**以及**对超参变化的不灵活**而不可行。为解决这一点，作者引入**存储侧转换卸载**：利用确定性 dataloader 提供的可预测顺序，以及存储节点上未被充分利用的 CPU，把计算密集的转换下推到存储层。这条"Just-in-Time"处理流水线让转换与训练重叠，同时降低延迟与停顿时间。

# 3 跨 DC 伴随评测

训练数千亿参数的大规模基础模型是一个昂贵而漫长的过程，涉及数千 GPU 连续运行数周乃至数月。在这种环境下，**尽早发现训练问题至关重要**。尽管监控训练 loss 是常见做法，作者的生产经验表明：**loss 和梯度范数这类"环内"信号并不是模型健康度的可靠指标**——一个模型可能训练 loss 看起来平稳，却已经在下游任务上表现出遗忘或崩溃。这一落差正是采用**伴随评测**的动因：一条持续的、带外的验证流水线，与训练并行地评估模型表现。在作者的部署中，伴随评测充当关键的安全阀，防止训练系统在一个已经发散的模型状态上继续推进。

在作者的生产环境中，伴随评测运行在往往位于不同数据中心的独立集群上。这一设计由两大约束驱动：

**其一**，预训练作业要求数千 GPU 严格同步执行，依赖 **gang scheduling** 维持齐步推进；因此把评测任务插进同一集群会**碎片化调度、拖累训练吞吐**。

**其二**，预训练必需最新一代加速器与高速互联以压缩 step 时间，而评测负载是**吞吐导向**的，可以在更老、更具成本效益的硬件上有效运行。这些评测集群通常部署在"哪里有电力与机位就放哪里"，结果往往与训练资源在物理上分离。

## 3.1 伴随评测工作流

图 1 的下半部分展示了伴随评测的端到端工作流。每次评测运行把一个分布式训练 checkpoint 转化为推理就绪的模型，然后执行 benchmark 负载。流程分三阶段：

**第一，checkpoint 合并（merging）**，把分布式 checkpoint 分片转换为推理就绪的各模态子模型。训练期间，训练框架把 checkpoint 写成许多分布式分片，这是为大型训练集群上的并行写而优化的。但对评测而言，这些分片必须被转换成 **safetensors** 这类标准推理格式。因此评测集群从远端存储取回相关参数分片，并**按模态分别执行合并**：重建完整的参数张量、丢弃优化器状态与其他推理不需要的张量、把每个合并后的模态子模型作为 safetensors 文件写入本地存储。

**第二，模型重分片（resharding）**，把合并后的 checkpoint 重新组织，以匹配评测集群的设备拓扑与并行配置。这一重塑确保推理能在可用设备上高效执行。

**第三，模型评测（evaluation）**，采用 client-server 架构。server 组件加载重分片后的模型并初始化 HTTP 服务端点；client 同时在各 benchmark 数据集上执行推理，以定量评估模型质量。系统把得到的指标写入存储，训练控制系统随后摄取这些指标。

这条工作流需要大量数据搬运与本地处理，其效率**直接被 checkpoint 合并期间观测到的网络与存储行为所塑造**。表 3 给出各阶段的数据量与时间分布。

**表 3：MM-L 模型各阶段的读写数据量与耗时**（checkpoint 合并阶段因跨 DC 流量而主导了 I/O 时间）

| 阶段 | 读 (GB) | 写 (GB) | 总耗时 | I/O 耗时 |
|---|---|---|---|---|
| Merging | 2631\* | 1742 | 2h 03m | 2h 03m |
| Reshard | 872 | 1435 | 18m | 18m |
| Evaluation | 8954 | 0 | 1h 55m | 4m |

## 3.2 Checkpoint 合并的瓶颈

作者的研究跨越 **30 天观察窗口，覆盖 19 个预训练任务**，模型参数量从小到大不等。这期间系统执行了 **3,589 次伴随评测**，通过识别出 **156 次关键模型回退**为运维效率做出了贡献。

但这一机制的价值依赖于**及时的反馈**。当评测结果被延迟，训练就会继续在一个发散的模型状态上推进——这既浪费训练 GPU 时间，也让恢复变得更难。

延迟的根源在于数据 I/O。对代表性的多模态大模型 MM-L，表 3 显示**单次评测周期可超过四小时，其中数据 I/O 约占端到端时间的 56.6%**。这个 I/O 瓶颈的代价是巨大的：在数据集中的 156 次回退上，I/O 引起的延迟浪费了约 **260 万 GPU 小时**，抵掉了评测系统本来能节省的 **550 万训练 GPU 小时**中的**将近一半**。

在这段漫长的数据 I/O 时间里，作者进一步发现 **84.8% 被 checkpoint 合并阶段消耗**——该阶段必须**通过广域网读取约 2.6 TB 数据**。与后续完全在本地存储上操作的阶段不同，checkpoint 合并需要跨数据中心取回张量，因而成为评测延迟的**首要来源**。具体地，作者识别出两个主要成因：

### 小 I/O 延迟陷阱

基于 Transformer 的模型由**成千上万个互不相连的张量**组成，尤其是那些细小的 **LayerNorm 参数与 Bias**。如图 3 所示，**MM-L checkpoint 中超过 60% 的张量小于 16 KB**。

由于 §3.1 描述的按模态合并只取回各子模型所需的参数张量，产生的读请求是**张量粒度**的，而非批量传输。即使合并服务器并发抓取张量，每个请求仍需经历数次**跨 DC WAN 往返**。这种碎片化与底层为**粗粒度 128 MB 块**优化的分布式文件系统配合得很差。这一错配产生两个后果：

- **读放大**：取一个 4 KB 张量往往需要在 HDFS DataNode 上读取一个明显更大的块，造成约 **1.5× 读放大**。
- **RTT 受限的吞吐**：在高延迟 WAN 链路（典型 **100 ms RTT**）上，这成千上万次小张量读的吞吐**由延迟而非带宽决定**。这表现为图 4 中的"**锯齿状**"吞吐模式——有效利用率跌至可用链路容量（即 **60 Gbps**）的一小部分。

> **图 3 解读**：典型 checkpoint 中张量大小的 CDF。横轴为张量大小（1 B 至 1 GB 对数刻度），曲线在很小的尺寸区间就已累积起相当高的比例，呈明显的阶梯上升。小张量的普遍存在放大了跨 DC 读取的延迟惩罚。
>
> **图 4 解读**：checkpoint 读取期间的吞吐（GiB/s）随时间变化，分读、写两条曲线。在标注为"Cross-DC read small tensors"的时段（约 1500–4000 秒区间），吞吐被压在很低的水平并呈锯齿状起伏；而在后段（约 6000 秒之后）出现若干高耸的尖峰。性能在抓取小张量时受制于跨 DC 链路的高 RTT。

### 带宽争抢

即便对大张量而言，跨 DC 带宽依然是一种被**平均 208 个并发任务**争抢的稀缺资源——这些任务包括数据迁移、日志聚合、并行评测等。图 5 展示了这种争抢：每任务的平均可用带宽波动剧烈，**常常退化到低于 1 GB/s**。朴素的"先来先服务（FCFS）"策略在此失效，因为它把延迟关键的评测与后台归档作业**不加区分地对待**。

> **图 5 解读**：生产环境中平均跨 DC 数据传输速率（GB/s），横轴为日期（11-24 至 12-08），画出 Mean、Top 10%、Bottom 10% 三条曲线。Mean 在约 0.5 至 1 GB/s 之间起伏，Top 10% 可冲到 3–4 GB/s，而 Bottom 10% 长期贴近于 0。带宽高度争抢且突发。

## 3.3 训练感知的 I/O 优化

为应对上述跨 DC I/O 瓶颈，作者施加两项**无需专用网络硬件**的训练感知优化。

**预测式 checkpoint 复制。** 伴随评测遵循可预测的间隔，典型为**每一千个训练步**一次。这种规律性使得——**训练系统一开始在既定间隔上保存 checkpoint，就可以立即启动流水线式的 checkpoint 复制**。与其让合并脚本发出成千上万次张量粒度的 WAN 读，存储系统把所需的 checkpoint 分片**批量聚成大块连续传输**，并缓存到评测集群的存储层。随后一个轻量的服务端命名空间服务 **NNProxy** 在这些本地缓存分片可用时，把评测作业导向从它们读取。这就**把大量广域网读转成本地读**，并从大多数计划内评测中**消除了跨 DC RTT 与小读碎片化**。

**信号驱动的优先级。** 并非所有评测都同等紧急。周期性评测遵循固定排期，而另一些是由训练异常（如 loss 尖峰或异常梯度行为）触发的——这类事件需要**更快的反馈**。作者引入一个简单的优先级信号，综合**模型规模、任务重要性、异常严重程度**。存储调度器用这个信号**抢占后台流量**、把网络带宽分配给紧急评测，从而在需要快速诊断时降低延迟。

## 3.4 评估

通过施加上述优化，作者把此前无人管理的 I/O 争抢转化为可预测的资源分配。这些训练感知机制：
- 使**平均 checkpoint 合并延迟降低 76.1%**，其中 T-S 模型达 **89.3%**、MM-L 模型达 **70.8%**；
- 把每次回退的 I/O 引发算力浪费从 **16,800 GPU 小时削减到 4,000 GPU 小时**；
- 在整个观察窗口内**总计挽回近 200 万 GPU 小时**。

## 3.5 未来方向

为在地理分布的集群间进一步提升性能，作者计划实施训练框架与存储层之间的**垂直协同设计**。两个方向尤其有前景：

**训练告知的存储控制（Training informed storage control）。** 训练框架应向存储控制面暴露诸如评测间隔、收敛指标等信号。这些信号能让存储系统**预判延迟敏感的操作**、据此分配资源、并避免来自后台流量的干扰。

**I/O 感知的 checkpoint 格式。** 标准分布式 checkpoint 布局几乎完全是为训练期间的高吞吐并行写而优化的，这本身就引入了困扰选择性跨 DC 读取的**结构性碎片化**。一个有前景的方向是设计**布局无关（layout-agnostic）或多布局（multi-layout）的 checkpoint 格式**。通过重构张量的分组方式——例如把碎片化的参数（如 LayerNorm 层与 bias）打包进**连续的、与存储块对齐的 extent**，同时把易变的优化器状态**隔离出去**——框架就能原生支持**零开销的选择性 WAN 流式读取**，而无需大量的服务端合并。

# 4 初始化 I/O 风暴

大规模模型训练的特征不是连续执行，而是**频繁的中断与重启**；这些来自硬件故障、自动化系统维护，以及最值得注意的——**模型开发过程中密集的调试循环**。

初始化是一道**完全同步的屏障**，因为训练必须等到每个 rank 都从存储重新加载完自己那一份最新 checkpoint 才能恢复。当数千个 rank 齐步重启时，它们在**同一瞬间**对极少量热文件发出并发读，把存储层变成启动阶段的瓶颈。

## 4.2 一场 I/O 风暴的解剖

为精确定位 checkpoint 加载缓慢的根因，作者做了一个**扩展到 2,048 GPU 的受控实验**，并对存储客户端插桩以分解每个 I/O 请求的延迟。

**与常见假设相反**——即认为分布式文件系统中元数据操作（`open`、`getattr`）才是瓶颈——作者的分析揭示**数据争抢才是首要元凶**。如图 7 所示，`open` 延迟保持低且稳定；然而 `read` 操作表现出**极端的尾延迟，且与 QPS 尖峰完美相关**。

> **图 7 解读**：默认 3 副本策略下 Read 与 OpenFile 操作的延迟与吞吐（QPS）。
> (a) Read 延迟：Avg / P99 / P99.9 / Max 四条曲线随时间（0–50 s）先升后降，在约 20–30 s 处形成峰值，Max 与 P99.9 明显爬升至 2 秒以上。
> (b) Read QPS：在 0–20 s 迅速升至约 120 KQPS 的平台，随后回落。
> (c) OpenFile 延迟：峰值仅在 40 ms 量级（注意单位是毫秒），远低于 read。
> (d) OpenFile QPS：峰值约 12 KQPS。
> 对比 (a) 与 (c) 的量纲差异，正是"瓶颈在数据而非元数据"的直接证据。

图 8a 绘出下载延迟的 CDF。该分布呈现**显著的长尾**——说明尽管大多数下载很快完成，仍有一小部分任务遭受极高延迟。作者的拆解显示，**这少数 straggler 读主导了完成时间，占总等待的 67.97%**。

通过在 **0.5 秒窗口**内计算每个文件的峰值 QPS，作者在图 8b 中观察到一个**重尾分布**。这里的"累积负载"表示对聚合峰值 QPS（即所有单文件峰值之和）的贡献。具体地，**Top 5% 的文件占据了这一总压力的 38.8%**。

> **图 8 解读**：(a) 文件下载的访问延迟 CDF——横轴延迟 0–7 秒，曲线在约 1–2 秒处已陡升至 0.8 以上，之后拖出长尾缓慢趋近 1。(b) 累积负载相对文件比例的分布——横轴为文件比例 0–1，纵轴为累积负载；曲线在文件比例较低的区间几乎贴地，只在接近 1 时急剧上翘，直观呈现负载高度集中在极少数文件上。

这些热点通常源自两个来源：**被所有 rank 访问的全局元数据文件**（如 `.metadata` 或 `common_states`），以及**更为重要的——由去重（redundancy elimination）造成的访问倾斜**。

这种倾斜是**当前 checkpoint 系统的副产物**：这些系统通过"**并行保存 + 去重**"来优先保障写吞吐与存储效率。这对写是有效的，但会造成**加载的不对称性**。作者用 Embedding 层与 MoE 层来说明这一问题：

- **Embedding 是被复制的参数**，系统为最小化开销**只持久化一份副本**；因此恢复这一层会触发**一对多的访问风暴**——数百个 rank 并发争抢**孤零零的一个文件**。在标准 3 副本策略下，有限的副本被这种并发请求压垮，延迟急剧上升。
- 相比之下，**MoE expert 是被分片的参数**，按其并行组被保存为**不同的文件**。这让 rank 的子集能并发访问不同文件，从而有效分散负载，**避免了在 embedding 层观测到的单点瓶颈**。

## 4.3 主动式热点预测

面对这一挑战，传统存储系统采用**反应式复制**：通过运行时监控探测热度，在阈值被突破时触发复制。在训练启动这一情境下，这种做法**根本上是有缺陷的**，原因有二：

**第一**，争抢窗口是**短暂的**（常常只持续几十秒）。等系统检测到热点并创建出新副本，加载阶段**已经结束了**。

**第二**，在 I/O 风暴期间发起复制流量，会与**已经饱和的网络带宽**竞争，从而**加剧而非缓解**瓶颈。

为克服这些限制，缓解必须是**主动的**——利用训练框架的信息，在风暴开始之前就把存储层准备好。

作者提出一种**协同机制**：训练框架通过 `SetReplicationHints` 接口，把即将到来的访问模式显式告知存储系统。由于训练配置（并行策略、world size）在**作业提交时就已知**，热文件的集合是**确定的**。框架识别两类数据：

- **全局元数据**：目标复制因子设为与作业 world size **N 成正比**；
- **被复制的张量**：基于 **tensor-to-rank 映射**聚合访问需求，为每个文件 *f* 确定预期并发度 **ω_f**。

收到这些 hint 后（通常紧接在 checkpoint 写完之后，或在作业被调度之前），存储系统按如下启发式策略主动复制识别出的热文件：

$$R_{target}(f) = \left\lceil \frac{\omega_f}{C_{load}} \right\rceil \tag{1}$$

其中 **C_load** 表示单个副本的**安全并发承载容量**。为防止存储膨胀，这些**临时（ephemeral）副本被打上 TTL（Time-To-Live）标签**，在启动阶段结束后自动回收。

## 4.4 评估与讨论

作者在 2,048 GPU 训练作业上评估主动式副本扩展。基于作业规模与预测出的 checkpoint 访问模式，策略在 checkpoint 恢复开始之前，把热元数据与被复制参数文件的**复制因子提升到 128**。

如图 9 所示，副本扩展从两方面改善 checkpoint 加载：

**第一**，**峰值聚合 Read QPS 提升**——这表明计算节点在存储上被阻塞的时间更少，能更激进地发出请求。

**第二，也更重要的是，平均读延迟下降**——因为最热的文件不再只由少数副本来服务。

**通过消除 straggler 读，checkpoint 加载总时间从 38.48 s 降到 22.78 s，改善 40.8%。**

> **图 9 解读**：默认 128 副本策略下 Read 与 OpenFile 的延迟与 QPS。
> (a) Read 延迟：注意纵轴单位已变为**毫秒**（200–800 ms 区间），相比图 7a 的秒级有数量级改善；峰值出现在约 10 s 处。
> (b) Read QPS：峰值攀升至约 **800 KQPS**（图 7b 为约 120 KQPS），说明请求发放能力大幅释放。
> (c) OpenFile 延迟：峰值约 250 ms 量级，出现在约 10 s。
> (d) OpenFile QPS：峰值约 17 KQPS。
> 整个加载过程的时间跨度也从图 7 的 50–70 s 收窄到 30–50 s。

尽管在这个受控的 2,048 GPU 实验中绝对节省只是秒级量级，但**运维影响随训练规模增长**。若不加干预，同步的 checkpoint 恢复会随着更多 rank 一起重启而制造出**愈发严重的争抢**。通过在恢复阶段之前就准备好副本，主动式副本扩展把一个**不可预测的、随规模变化的存储瓶颈，转化为一个更稳定的加载过程**。

基于这些结果，作者为生产环境**固化了复制准则**：**10K GPU 集群用 64 副本，20K GPU 集群用 128 副本**。

**副本扩展的收益取决于训练并行策略如何在 checkpoint 时物化模型状态。** 作者讨论了三种情形：

**最有利的情形**：完全分片数据并行（fully sharded data parallelism）**本身就已经**把参数分片散布到各 rank 与各文件上。剩余的不均衡通常只来自一小组共享结构——如 checkpoint 元数据、common states，或其他非分片张量。**只扩展这些结构**往往就足以让恢复负载在存储副本间良好均衡，且存储开销很小。

**常见的生产情形**虽不那么理想，但仍然高度可针对：每个 rank 通常只保存少量张量、常常就是**一个**张量，所以大多数文件归属清晰；而被复制的张量与全局状态仍会造成少数热文件。副本扩展在此有效，因为系统**只需扩展这一小部分热子集**，而不必提高整个 checkpoint 的复制因子。

**较不利的情形**出现在：一个被复制的张量与**大得多的分片参数分片被打包在同一个 checkpoint 文件里**。由于复制决策是在**文件粒度**上做出的，为那个共享张量扩展该文件，也会连带复制无关的分片数据。

## 4.5 未来方向

为在更大训练规模上进一步改善 checkpoint 恢复，未来系统可以让 **checkpoint 文件布局**与**恢复时的 fanout** 更好地与副本扩展对齐。

**去重感知的 checkpoint 打包（Deduplication-aware checkpoint packing）。** 一个自然的扩展是：在划分张量保存任务时就**考虑恢复时的复制需求**。那些被激进去重、因而在恢复期间很可能被众多 rank 读取的张量，应当被放入**专用文件**，或与**需要相似副本扩展的张量共同打包**。这种布局让**文件级的副本决策与张量级的需求保持对齐**：扩展一个热文件就能为共享读增加容量，而不必同时拷贝大量无关的分片。

**通信辅助的 checkpoint 加载（Communication-assisted checkpoint loading）。** checkpoint 恢复的加载计划**本身就已指明哪些 rank 共享同一 checkpoint 分片**，这正提供了组织"通信辅助 fanout"所需的信息。取决于部署规模、rank 局部性、以及框架集成方面的约束，未来系统可以通过**额外的存储副本**、一条**范围受限的 broadcast 路径**，或**两者的混合**来服务一个热分片。

# 5 MM-L 转换之墙

在传统的纯文本模型训练中，数据加载过程**有效地被隐藏在 GPU 计算之后**：数据读取与轻量的 tokenization 在每一步开始之前就早已完成，使训练循环保持计算受限。

然而，随着训练从纯文本模型转向多模态模型，dataloader 不仅要服务文本，还要服务音频、视频、图像等异构数据。结果是，多模态训练的数据加载**再也无法与 GPU 执行完全重叠**，导致输入流水线**大幅超出计算时间**，成为训练停顿的**主导来源**。

## 5.1 确定性 Dataloader

作者环境中的多模态训练使用一种**确定性 dataloader** 架构。不同于 PyTorch DataLoader 或流式 dataloader 那类会因**动态 shuffle 计算与复杂状态管理**而产生运行时开销的标准加载器，作者的方法利用一份**离线生成的全局执行计划**。这既保证了在数千个 worker 之间**严格确定的顺序**，又实现了**全局随机 shuffle**。

图 10 展示了用来组织与提供原始训练数据的**三种数据格式**：

**合并二进制 bin（consolidated binary bins）。** 底层上，系统依赖合并二进制 bin——音频、视频、以及拼接后的图像与文本等原始多模态数据，被作为**大块连续二进制文件**存放在全局存储系统中。作者选择 **20 GB 的 bin 大小**，以在**文件管理开销**与**合并 bin 的代价**之间取得平衡；这提供了**精确的字节范围访问**，而没有 Parquet 这类列式格式常见的读放大。

**元数据映射（metadata maps）。** 为实现快速查找，作者采用元数据映射作为**逻辑到物理的翻译层**，把 sample 标识符转换为二进制 bin 内的**字节偏移与长度**。生产数据集包含大约**一万个 map 文件，总计约 0.7 TB**。

**每步 info 文件（per-step info files）。** 最后，作者用每步 info 文件来管理顺序。由于每个训练 epoch 都以打乱的顺序消费全部样本，系统会生成一个文件，列出**待读取 sample 标识符的精确序列**。这使得 **shuffle 完全通过离线置换索引项来完成**——在**不触碰、不重写底层物理数据**的前提下获得一个新的全局顺序。

> **图 10 解读**：确定性 dataloader 的磁盘格式结构与数据加载流水线。图的底层是 Bin 1 / Bin 2 / Bin 3（存放视频、音频、文本等混合内容）；中间一层是 Metadata Map，其中 Sample N₁ 由 {video, offset, length} 与 {audio, offset, length} 两条项构成、Sample N₂ 由 {video, offset, length} 与 {text, offset, length} 构成，箭头指向底层各 bin；再上一层是 Step Info（Step N−1 / Step N / Step N+1）；顶部是 Dataloader，通过 ① load data 从下方取数、② transform 调用左侧的 Pre-Processors（Video Decoder、Resolution Scaler、Audio Normalizer 等）、③ transfer 把结果送往右侧的 GPUs。

训练期间，dataloader 按以下序列为下一个训练步准备数据：

- **元数据解析（Metadata resolution）**：dataloader 首先读取每步 info 文件，取得即将到来的这一批所需的 sample 标识符。然后查询元数据映射，把这些标识符翻译为合并二进制 bin 内的字节偏移与长度。

- **数据检索（Data retrieval）**：使用解析出的偏移，dataloader 发出 `read` 或 `pread` 系统调用，从二进制 bin 中取回相应的字节范围。这一阶段对底层文件执行**随机访问**，只取回当前批次所需的具体样本。

- **样本转换（Sample transformation）**：原始字节取回后，dataloader 施加**模态特定的转换**。例如视频样本会经历视频解码、抽帧、裁剪等一系列操作，随后转换为张量；而图像样本会被解码、缩放、转换为张量。**这些操作在宿主 CPU 上执行**，以避免基于 GPU 的转换所带来的巨大内存开销，并让 GPU 资源专注于模型计算。得到的张量被**暂存**，以便在下一步开始时传输到 GPU。

多模态数据的**异构本质**——把短文本与高分辨率图像、长视频片段混在一起——引入了转换成本上的**巨大变异性**。图 11 对比了 T-L 与 MM-L trace 中跨主机的最大数据加载延迟：T-L 负载显示出**紧密聚集**的延迟，而 MM-L 负载呈现**显著的长尾**。例如在采样期内，**最慢的主机可耗时 42.72 s，而该步的平均数据加载时间为 5.35 s——单单这一步就产生 37.4 s 的落差**。

这种变异性是由**多模态数据集中的样本长度方差**驱动的，**而不是某种瞬时的存储问题**。为保持训练覆盖度，MM-L 的批次同时包含轻量样本和长视频片段，后者的转换成本随**时长、编码复杂度、抽帧数量**而增长。随着 **GPU step 时间不断缩短**，这种宿主侧长尾**越来越难被模型计算所掩盖**。

在采样阶段中，一台处理 **161.9 MB** 样本的主机需要 **41.5 秒**完成转换，由此造成时间波动；相比之下，其他主机平均只处理约 **20 MB**，在 **5.05 秒**内完成转换。在极端情况下，被分配到一个约 10 分钟、**500 MB H.264 视频**的机器，**即便使用 decord 的硬件加速解码与四个并发解码线程，解码与抽帧仍需超过 2.18 分钟**。这样的 straggler **迫使数千 GPU 空转等待它们完成**。

图 12 展示了训练步时长的方差。作者发现，**对单个 step，跨主机的执行时间差可达 5 秒**，迫使其他节点等待 straggler。这种时间倾斜**直接转化为每天超过 10,000 GPU 小时的浪费**。

> **图 12 解读**：跨不同机器的训练步时间差。横轴为 step 编号（0–800+），纵轴为 Max Step Difference（0–5 s）。曲线基线在 0.5 s 上下密集抖动，间杂出现若干高尖峰——在约 150、250、400、600、780 等位置分别冲到 3–5 秒。

## 5.3 存储侧转换卸载

解决这一瓶颈需要**降低转换阶段的成本**。虽然执行**离线转换**（即在训练前就把原始样本解码并转换为可直接训练的张量）看起来是个直截了当的方案，但它在生产规模上**不可行**，有两个根本原因：

**第一，存储放大使得存储解码后数据的代价高得无法承受。** 高分辨率图像与视频通常以 **JPEG、H.265** 这类空间高效的格式归档。把它们解码为 float 张量会造成**极端的存储膨胀**：**视频的存储足迹增长超过 40×**，图像的膨胀虽然小一些但仍然可观——**达数十倍**。在 PB 级规模上，解码后的表示将需要 **EB 量级的存储**，这只是把瓶颈**从在线 CPU 转换转移到了原始存储容量**上。

**第二，离线转换有着固有的不灵活性。** 所需的转换严重依赖模型超参——如**裁剪尺寸、帧数、分辨率**——而这些在不同的预训练 run 之间都会变化。对模型架构或数据增广策略的**任何改动，都需要完整重新生成**预转换后的数据集。这个过程会消耗数百万 GPU 小时，并**显著拖慢模型开发速度**。

**取而代之，作者利用一种"已经付过钱"的资源：高吞吐集群中的存储节点往往有未被充分利用的 CPU 容量。** 当训练主机被模型计算与媒体处理占满时，存储节点通常是被**网络或磁盘带宽**卡住的，从而留下**大量闲置的计算容量**。

这一机会源自作者集群中一种**根本性的 I/O–计算错配**。作者观察到：训练节点是**计算/内存饱和**的，而存储节点通常受制于 **HDD 寻道延迟或网卡（NIC）上限**。遥测数据表明，**存储节点 CPU 常常处在 20–30% 的利用率，在等待 I/O 中断**——这正是作者用来隐藏格式转换成本的资源缺口。

作者**重新设计存储层，使其不仅是数据仓库，更是一个"解耦的预处理引擎"（Disaggregated Pre-processing Engine）**。这一设计从根本上是由 §5.1 那个确定性 dataloader 的**严格确定性**所使能的：既然数据消费序列已固定在全局索引中，存储系统就能**准确预测未来的数据访问模式**，从而用它的**空闲核心**去执行转换。

作者实现了一个 **Pushdown Transformation Engine（下推转换引擎）**，含三个核心机制：

**调度同步（Schedule synchronization）。** 训练初始化时，训练框架把**数据集标识符与 step 进度**共享给存储系统。存储节点由于能访问每步 info 文件，可以**自主推导出即将到来的数据块序列**。这**消除了训练客户端在关键路径上发出数百万次数据与元数据操作 RPC 的需要**。

**Just-in-Time（JIT）转换。** 存储节点为训练作业维护一个 **Consumer Queue（消费者队列）**。它们**推测性地读取**原始二进制数据，并在后台执行已注册的**转换图**——例如解码、随机裁剪、归一化。这种流水化确保：**当 GPU 在计算第 N 步时，存储层已经在为第 N+1 步准备张量**。

对视频样本，存储侧引擎还会在数据回传到训练集群**之前先施加抽帧（frame sampling）**。这让**网络负载保持有界**，尽管解码带来了临时的体积膨胀；同时**防止格式膨胀本身变成一个新的尾延迟来源**。

**负载感知回退（Load-aware fallback）。** 为防止把存储节点打满，作者实现了**动态背压**以保障存储稳定性——这在共享的生产环境中是一条**硬约束**。**如果某个存储节点的 CPU 使用率超过安全阈值（例如 80%），它就中止转换、把原始字节返回给训练 dataloader。** 训练客户端**检测数据格式（Tensor 还是 Binary）**，并回退到本地处理。这种混合方式让作者既能用存储机群的**聚合算力吸收转换的尖峰**，又能**保护存储控制面免于过载**。

## 5.4 评估

这一架构在生产环境中带来显著改善，验证了"把计算搬到存储层"的有效性。具体地：
- 通过把重活卸载到存储池，**P99 数据加载延迟下降 85.7%**，有效缓解了 straggler 效应；
- 在训练效率方面，**由转换 straggler 造成的停顿时间减少 63.2%**，折算为 **MFU 的相对提升 10.8%**；
- 在资源利用方面，观察到**训练主机上数据加载的 CPU 占用下降 94%**，实际上**消除了宿主侧的瓶颈**。

## 5.5 未来方向

存储侧转换卸载**依赖于存储层中同置的计算余量**。这一假设在作者的环境中成立，因为同一批存储集群还支撑着大规模数据处理，在等待磁盘或网络时常有**空闲 CPU 周期**。但它**对云对象存储或精简型存储设备可能不成立**——这类系统在数据近端几乎不暴露可编程的计算。在那些情形下，也存在其他技术可用于改善转换性能、减少训练放缓：

**已处理样本的缓存（Processed-sample caching）。** 如先前工作所建议，当训练**反复重访数据**时，缓存预处理后的样本可以与存储侧卸载互补。但在本文关注的**大规模预训练**中，全局 shuffle 后的样本**很少在缓存的有效生命周期内被重访**，所以已处理数据的缓存**几乎带不来命中率收益，反而增加一致性与容量压力**。而在**存在重复样本访问的场景**中——例如**强化学习**，或在较小语料上做**重复微调**——缓存就变得有效，并且可以存放存储侧引擎产出的转换结果。

**预测式、转换感知的组批（Predictive transform-aware batching）。** 既然确定性 dataloader **离线就知道精确的样本序列**，就可以用一个**轻量的成本模型**，基于**原始样本大小、编码格式、分辨率、片段时长**等元数据，**提前预测每个样本的转换成本**。有了这些估计，批次就可以被组织成**在各主机间均衡转换成本**——把重样本与轻样本搭配起来，使**没有任何单一主机被分配到不成比例的昂贵片段**。

# 6 如果换成别的做法呢？（What If?）

为 EB 级预训练构建高效数据流水线，必须在**存储成本、计算效率、工程复杂度**之间权衡。在运维历程中，作者批判性地评估了若干最终因"在规模上不实用"而被舍弃的替代方案。这一节以一系列"What If"问句展开讨论。

## Q1：如果用点对点（P2P）分发来做模型加载呢？

在第 4 节，作者是通过在存储节点上主动复制数据来应对初始化风暴的。虽然 P2P 分发（如 NCCL、UCX）**理论上随集群规模线性扩展**，作者仍严格优先选择**层级式的 client-server 模型**，以缓解**多租户干扰**与**尾延迟敏感性**。

**第一**，大型 GPU 集群会**并发执行多个训练任务**。P2P 那种无结构的 all-to-all 流量模式会**引发网络拥塞、打满缓冲区**，并**扰乱并发作业中对延迟敏感的 NCCL 集合通信**。

**第二**，训练初始化是一道**受最慢节点约束的同步屏障**。而 P2P 的性能**本质上是概率性的**——**单个**因限流或本地拥塞而变慢的 peer，就会**延迟整个 gang 的启动**。

相比之下，作者的层级式复制提供了**确定的 SLA**、把流量**限制在南北向**，从而有效地把集群与跨租户干扰、以及概率性的尾延迟**隔离开来**。

## Q2：如果部署一个专用转换集群，作为存储侧处理的替代方案呢？

在第 5 节，作者是通过把计算卸载到存储节点来应对多模态转换开销的。一个替代方案是**专用的样本转换集群**——一支 CPU 丰富的机器组成的机群，先解码转换数据，再把张量转发给训练主机。这种架构以 **tf.data service** 和 **Ray Data** 为代表，把数据准备与训练**解耦**。作者因**显著的网络放大**与**运维开销**而否决了这一设计。

**第一，解码后的张量远远大于其压缩源。** **视频解压使数据量膨胀 50–100×**；把这些张量在数据中心网络上传输，会**把瓶颈从 CPU 转移到带宽**，并**打满共享的网络 fabric**。

**第二，独立集群引入配置（provisioning）复杂性**：容量必须**按多模态峰值需求来配**，却在**纯文本负载期间处于闲置**。

相比之下，作者的存储侧卸载利用的是**存储节点上已经配置好的空闲 CPU 周期**，从而**避免网络放大**，也**消除了对专用资源池的需要**。

## Q3：如果迁移到专门的 AI-native 存储系统，作为 HDFS 的现代替代呢？

近期工作提出了专门的 AI 存储系统（如 **3FS、AIStore**），它们提供**更优的小文件性能**与**kernel-bypass 网络**。作者之所以保留并优化一个"老"的大数据系统、而非采用全新（greenfield）方案，主要出于**数据引力（data gravity）**与**运维连续性**。

**HDFS 是作者的统一数据湖**，承载着**AI 训练之外的多条业务线**的 EB 级数据。把这个体量迁移到一个新系统，在**运维上不可行、成本上不可承受**。

此外，AI-native 系统往往**要求特定的硬件配置**（如全 NVMe），或需要**定制客户端**，从而**破坏与更广生态的兼容性**（例如基于 Spark 的数据清洗流水线）。

作者的工作证明：**通过暴露应用层的模式，像 HDFS 这样的老系统能够满足严苛的 LLM 训练需求，而无需整体替换。** 这种软件定义的路径使得**渐进式的基础设施演进**成为可能，同时**维持服务稳定性**。

# 7 相关工作

## 面向模型训练的存储基础设施

传统的**并行文件系统（PFS）**如 **Lustre** 与 **GPFS** 提供高 checkpoint 带宽，但**在多模态数据集的巨量元数据压力下退化**。反过来，解耦式的**对象存储**如 **S3** 与 **Azure Blob** 提供了可扩展性，但**延迟高、随机访问吞吐受限**。

新兴的 **AI-native 系统**（如 **3FS、AIStore**）虽然通过 kernel-bypass 网络与专用缓存解决了上述局限，但**往往要求全新部署**。如第 6 节所详述，把 EB 级的遗留数据迁移到专用技术栈**在运维上不可行**。

作者的工作证明：**通过暴露应用层的确定性，通用大数据系统（HDFS）能够满足严苛的训练 SLA，而无需根本性的架构替换。**

## 数据加载与全局协调

已有研究通过**领域特定的缓存**（如 **Quiver**、**SiloD**）或**协同取数**（如 **CoorDL**）来优化数据加载。这些系统**主要是反应式的，依赖运行时的命中率**。相比之下，作者的**确定性 dataloader（§5.1）利用 LLM 训练的确定性，把随机访问转化为顺序流**。

在**数据格式**方面，**TFRecord、WebDataset、Lance** 这类方案通过聚合样本来缓解随机寻道，但**使全局 shuffle 变得复杂**。作者的**索引式方法在不做物理数据搬运的前提下确保全局随机性**。

最后，虽然 **CrossPipe** 这类工作优化的是**流水线调度**，作者处理的是**伴随评测的存储物流**问题（§3）——通过**命名空间级的预测式 checkpoint 复制**来掩盖跨 DC 延迟。

# 8 结论

作者识别出大规模预训练中的关键存储瓶颈，包括**伴随评测期间的跨 DC 延迟、初始化风暴、以及多模态转换开销**。通过**利用负载的确定性**，作者实现了若干软件定义的优化——**预测式 checkpoint 复制、主动式复制、存储侧卸载**——从而**把存储层转变为一个主动的合作伙伴**。这些机制显著降低了伴随评测延迟、启动时间、以及数据加载停顿。

**作者的工作证明：像 HDFS 这样的老系统，能够通过垂直协同设计（vertical co-design）有效地支撑 EB 级训练。**
